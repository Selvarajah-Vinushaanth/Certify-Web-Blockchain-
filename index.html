1. What Is Blockchain?

A blockchain is a distributed, immutable digital ledger that records transactions across a network of computers. Think of it as a shared notebook that everyone can read, but no one can erase or alter once something is written.

1.1 The Simple Analogy

Imagine a classroom register:
  • Every student has an identical copy of the attendance register
  • When a new entry is made, ALL copies are updated simultaneously
  • No single person can erase or change a past entry — because everyone else's copy would show the original
  • If someone tries to cheat, their copy won't match the majority — so the fake is rejected

That's essentially how blockchain works!

1.2 Key Properties of Blockchain

PropertyWhat It Means
DecentralizedNo single authority controls the data — it's shared across many computers (nodes)
ImmutableOnce recorded, data cannot be changed or deleted
TransparentAll participants can view the entire history of transactions
TrustlessYou don't need to trust any individual — the system's math ensures honesty
DistributedIdentical copies exist on thousands of computers worldwide

2. How Blockchain Works — Core Concepts

2.1 Blocks

A block is a container that holds a batch of transactions. Each block contains:

Structure of a Block

├─────────────────────────────────────────┤

│    • Previous Block Hash: 0x8a3f...     │
│    • Timestamp: 2026-03-30 10:15:00     │
│    • Nonce: 7839241                     │
│    • Merkle Root: 0x4b2e...             │

│  Transactions:                          │

├─────────────────────────────────────────┤
│  This Block's Hash: 0x7c91...           │
└─────────────────────────────────────────┘

2.2 The Chain

Blocks are linked together using cryptographic hashes. Each block contains the hash of the previous block, creating an unbreakable chain:

How Blocks Link Together
Block #1
Hash: 0xABC
Prev: 0x000
→
Block #2
Hash: 0xDEF
Prev: 0xABC
→
Block #3
Hash: 0x123
Prev: 0xDEF
→
Block #4
Hash: 0x456
Prev: 0x123
Why is this secure? If someone changes data in Block #2, its hash changes. But Block #3 stores Block #2's original hash — so the chain breaks instantly. Every node in the network would reject the tampered version.

2.3 Nodes and the Peer-to-Peer Network

A blockchain runs on a peer-to-peer (P2P) network — a collection of computers (called nodes) that communicate directly with each other, with no central server.

2.4 Transactions

A transaction is any action recorded on the blockchain. In cryptocurrency, it's a transfer of coins. In Ethereum, it can also be a smart contract call.

Lifecycle of a Transaction:

1. Create: User creates and signs the transaction with their private key
↓
2. Broadcast: Transaction is sent to the network and enters the mempool (waiting area)
↓
3. Validate: Nodes check: Does the sender have enough funds? Is the signature valid?
↓
4. Include in Block: A miner/validator picks the transaction and includes it in a new block
↓
5. Confirm: The block is added to the chain. Transaction is now permanent!

2.5 Merkle Trees

Blockchains use Merkle Trees to efficiently organize transactions within a block. It's a tree structure where:

  • Each leaf node = hash of a transaction
  • Each parent node = hash of its two children combined
  • The root (Merkle Root) = a single hash representing ALL transactions
Merkle Tree Structure
                    Merkle Root
                   ┌────┴────┐
               Hash(AB)    Hash(CD)
              ┌───┴───┐  ┌───┴───┐
          Hash(A)  Hash(B)  Hash(C)  Hash(D)
            │        │        │        │
           TX-A    TX-B     TX-C     TX-D
Why Merkle Trees? To verify a single transaction, you don't need to download the entire block. You only need the hashes along the path from the transaction to the root — this is called a Merkle Proof. This makes light nodes (like mobile wallets) possible.

4. Consensus Mechanisms

Since there's no central authority, blockchain nodes must agree on which transactions are valid and in what order. This agreement process is called a consensus mechanism.

4.1 Proof of Work (PoW)

Used by: Bitcoin, Ethereum (before Sept 2022)

How it works:

  1. Miners compete to solve a complex mathematical puzzle
  2. The puzzle: Find a number (nonce) such that the block's hash starts with a certain number of zeros
  3. This requires enormous computational power (trial and error)
  4. The first miner to solve it broadcasts the block
  5. Other nodes verify the solution (easy to verify, hard to solve)
  6. Winner receives a block reward (cryptocurrency)
Example PoW puzzle:
  Find nonce such that:
  SHA256("block_data" + nonce) → "0000000....."  (starts with 7 zeros)

  Try nonce = 1    → hash = "7f3a8b..."  ✗
  Try nonce = 2    → hash = "a12c4d..."  ✗
  Try nonce = 3    → hash = "e9f012..."  ✗
  ... millions of attempts ...
  Try nonce = 8392741 → hash = "0000000a8f..." ✓ FOUND!
Downside: PoW uses massive amounts of electricity. Bitcoin mining consumes more energy than some countries!

4.2 Proof of Stake (PoS)

Used by: Ethereum (after "The Merge" — Sept 2022), Cardano, Solana

How it works:

  1. Validators stake (lock up) their cryptocurrency as collateral
  2. The protocol randomly selects a validator to propose the next block
  3. Selection probability is proportional to the amount staked
  4. If the validator acts honestly → earns rewards
  5. If the validator cheats → loses their staked funds (slashing)

4.3 Comparison Table

5. Cryptography in Blockchain

Blockchain relies heavily on cryptographic techniques for security. Understanding these is essential.

5.1 Hash Functions

A hash function takes any input and produces a fixed-size output (the "hash" or "digest"). Blockchain primarily uses SHA-256 (Bitcoin) and Keccak-256 (Ethereum).

Properties of a Good Hash Function:

PropertyMeaning
DeterministicSame input always gives the same output
FastQuick to compute
Avalanche EffectChange 1 bit of input → completely different hash
One-WayCannot reverse-engineer the input from the hash
Collision-ResistantNearly impossible to find two different inputs with the same hash
Example (SHA-256):
  Input: "Hello"        → Hash: 185f8db32271fe25f561a6...
  Input: "Hello!"       → Hash: 334d016f755cd6dc58c533...
  Input: "hello"        → Hash: 2cf24dba5fb0a30e26e83b...

  Tiny changes → completely different hash!

5.2 Public-Key Cryptography

Every blockchain user has a key pair:

Key Pair
Private Key
Secret! Never share.
Used to SIGN transactions
e.g., 0x4c0883a6...
→ generates →
Public Key
Share freely
Used to VERIFY signatures
e.g., 0x04bfcab...
→ derives →

e.g., 0x71C7...3E4b
Critical Rule: Your private key is like your bank password. If someone gets it, they control all your funds forever. There is NO "forgot password" in blockchain!

5.3 Digital Signatures

When you send a transaction, you sign it with your private key. This proves:

  1. Authentication — You are the owner of the account
  2. Integrity — The transaction hasn't been tampered with
  3. Non-repudiation — You can't deny sending it
Signing Process:
  1. Create transaction: "Send 1 ETH to 0xBob..."
  2. Hash the transaction data
  3. Sign the hash with your private key → Signature
  4. Broadcast: transaction + signature to the network

Verification Process (by any node):
  1. Receive transaction + signature
  2. Use sender's PUBLIC key to verify the signature
  3. If valid → transaction is authentic ✓

6.2 Ethereum Virtual Machine (EVM)

The EVM is the runtime environment for smart contracts on Ethereum. Think of it as a giant, global computer:

  • Every Ethereum node runs the EVM
  • Smart contract code executes identically on every node
  • Results are deterministic — same input always gives the same output
  • The EVM is sandboxed — contracts can't access the internet or local files

7. Smart Contracts & Solidity

7.1 What Is a Smart Contract?

A smart contract is a self-executing program stored on the blockchain. It runs automatically when predefined conditions are met — no middleman needed.

Real-World Analogy: A vending machine is a simple smart contract:
  • Condition: Insert $2
  • Action: Dispense a drink
  • No cashier needed. The machine (contract) enforces the rules automatically.

7.2 Solidity — Ethereum's Programming Language

Solidity is the most popular language for writing smart contracts. Its syntax is similar to JavaScript/C++.

Basic Structure of a Solidity Contract:

// SPDX-License-Identifier: MIT       ← License identifier
pragma solidity ^0.8.24;              ← Compiler version

contract MyFirstContract {            ← Contract declaration

    // State variables (stored on blockchain permanently)
    string public message;
    address public owner;
    uint256 public count;

    // Constructor — runs ONCE when contract is deployed
    constructor(string memory _msg) {
        message = _msg;
        owner = msg.sender;       // msg.sender = whoever deploys
    }

    // Function — can be called by anyone
    function updateMessage(string memory _newMsg) public {
        message = _newMsg;
        count += 1;
    }

    // View function — reads data, no gas cost
    function getMessage() public view returns (string memory) {
        return message;
    }
}

7.4 Events

Events are logs emitted by smart contracts. They're stored on-chain but are NOT accessible from within contracts — they're designed for off-chain applications (like your frontend) to listen for changes.

// Declaring an event
event CertificateIssued(
    bytes32 indexed certId,
    address indexed issuer,
    address indexed recipient,
    string ipfsCid
);

// Emitting the event inside a function
emit CertificateIssued(certId, msg.sender, _recipient, _ipfsCid);
The indexed keyword allows you to filter events by those fields — like searching for "all certificates issued by address 0x123..."

7.5 Modifiers (Access Control)

Custom modifiers restrict who can call certain functions:

modifier onlyOwner() {
    require(msg.sender == owner, "Only owner can call this");
    _;    // ← this is where the function body executes
}

modifier onlyIssuer() {
    require(authorisedIssuers[msg.sender], "Not an authorised issuer");
    _;
}

// Usage:
function addIssuer(address _issuer) external onlyOwner {
    authorisedIssuers[_issuer] = true;
}

7.6 Real Example — Certificate Verification Contract

contract CertificateVerification {

    enum CertStatus { None, Active, Revoked }

    struct Certificate {
        bytes32 certHash;       // keccak256 hash of the PDF
        string  ipfsCid;        // IPFS content identifier
        address issuer;         // university address
        address recipient;      // student wallet
        string  studentName;
        string  courseName;
        uint256 issuedAt;
        CertStatus status;
    }

    mapping(bytes32 => Certificate) public certificates;
    mapping(address => bool) public authorisedIssuers;

    function issueCertificate(...) external onlyIssuer {
        // Creates a certificate record on-chain
    }

    function verifyCertificate(bytes32 _certId)
        external view returns (bool valid, ...) {
        // Anyone can verify — it's a VIEW function (free!)
    }

    function revokeCertificate(bytes32 _certId) external onlyIssuer {
        // Only the original issuer can revoke
    }
}

8. Hardhat — Development Framework

8.1 What Is Hardhat?

Hardhat is the most popular development environment for building Ethereum smart contracts. It provides:

  • Local blockchain — a simulated Ethereum network on your computer
  • Compiler — compiles Solidity to EVM bytecode
  • Testing framework — write and run automated tests
  • Deployment scripts — automate contract deployment
  • Debugging tools — stack traces and console.log in Solidity

8.6 What Is an ABI?

ABI (Application Binary Interface) is a JSON description of your contract's functions. It tells the frontend HOW to communicate with the contract.

// ABI defines what functions exist and their parameters:
[
  "function issueCertificate(bytes32 _certHash, string _ipfsCid, address _recipient, string _studentName, string _courseName) returns (bytes32)",
  "function verifyCertificate(bytes32 _certId) view returns (bool valid, string studentName, ...)",
  "event CertificateIssued(bytes32 indexed certId, address indexed issuer, ...)"
]
Think of ABI like a restaurant menu — it tells you what functions are available, what inputs they need, and what they return. Without the ABI, the frontend can't talk to the contract.

8.7 Deployment Script

// scripts/deploy.js
const { ethers } = require("hardhat");

async function main() {
  // Get the contract factory (compiled code)
  const CertVerification = await ethers.getContractFactory(
    "CertificateVerification"
  );

  // Deploy it to the blockchain
  const contract = await CertVerification.deploy();
  await contract.waitForDeployment();

  // Get the deployed address
  const address = await contract.getAddress();
  console.log("Contract deployed to:", address);
}

main().catch(console.error);

9. MetaMask — Your Crypto Wallet

9.1 What Is MetaMask?

MetaMask is a browser extension (Chrome/Firefox/Brave) that serves as your Ethereum wallet and gateway to blockchain applications. It:

  • Stores your private keys securely in your browser
  • Signs transactions on your behalf
  • Connects to DApps (decentralized applications)
  • Lets you switch between networks (mainnet, testnets, local)

9.2 MetaMask Concepts

Seed Phrase (Recovery Phrase)

When you create a MetaMask wallet, you receive a 12-word seed phrase. This is the MASTER KEY to all your accounts. If you lose it, you lose access forever. Write it down on paper — never store it digitally. 
Example: apple banana cherry dragon elephant fountain grape
         hotel igloo jungle kangaroo lemon

Account Structure

Seed Phrase (12 words)
  └── generates → Private Key #1 → Public Key #1 → Address #1 (Account 1)
  └── generates → Private Key #2 → Public Key #2 → Address #2 (Account 2)
  └── ... infinite accounts from one seed phrase

9.5 Transaction Signing with MetaMask

When your DApp wants to write to the blockchain (e.g., issue a certificate):

  1. DApp creates the transaction details
  2. MetaMask shows a popup: "Confirm Transaction — Gas: 0.003 ETH"
  3. User clicks Confirm

  5. Transaction is sent to the blockchain
MetaMask never reveals your private key to the website! The signing happens inside MetaMask. The DApp only receives the signed transaction.

10. IPFS — Decentralized File Storage

10.1 The Problem

Storing files (PDFs, images, documents) directly on the blockchain is extremely expensive. Storing just 1 KB of data on Ethereum costs several dollars in gas fees. A 1 MB PDF would cost thousands of dollars!

Solution: Store the file on IPFS and only store the file's hash/CID on the blockchain (just 32 bytes — very cheap).

10.2 What Is IPFS?

IPFS (InterPlanetary File System) is a decentralized, peer-to-peer file storage system. Unlike traditional web hosting:

Traditional Web (HTTP)IPFS
Location-based: "Get file from server at example.com"Content-based: "Get file with hash QmXyz..."
Server goes down → file goneFile exists on any node that has it
Server owner can modify the fileContent is immutable (hash changes if file changes)
Centralized — single point of failureDecentralized — distributed across nodes

10.3 Content Identifier (CID)

Every file uploaded to IPFS gets a unique CID (Content Identifier) — a hash of the file's content.

Upload "certificate.pdf" to IPFS:

  CID = "QmXoypizjW3WknFiJnKLwHCnL72vedxjQkDDP1mXWo6uco"

Access it via gateway:
  https://gateway.pinata.cloud/ipfs/QmXoypizjW3WknFiJnKLwHCnL72vedxjQkDDP1mXWo6uco

Key Properties:
  ✓ Same file → always same CID
  ✓ Different file → different CID
  ✓ Cannot modify the file at this CID
  ✓ Anyone with the CID can access the file

10.4 Pinata — IPFS Pinning Service

Pinata is a popular IPFS pinning service. Since IPFS nodes can remove unpopular files (garbage collection), you need a pinning service to ensure your files stay available permanently.

How Pinata Works:

1. You upload a file to Pinata via their API
↓
2. Pinata stores it on their IPFS nodes and pins it (prevents garbage collection)
↓
3. Pinata returns the CID
↓
4. Anyone can access the file via: https://gateway.pinata.cloud/ipfs/{CID}

Code Example — Uploading to IPFS via Pinata:

import axios from "axios";

async function uploadToIPFS(fileBuffer, fileName) {
  const formData = new FormData();
  formData.append("file", new Blob([fileBuffer]), fileName);
  formData.append("pinataMetadata", JSON.stringify({ name: fileName }));

  const response = await axios.post(
    "https://api.pinata.cloud/pinning/pinFileToIPFS",
    formData,
    {
      headers: {
        pinata_api_key: "YOUR_API_KEY",
        pinata_secret_api_key: "YOUR_SECRET_KEY",
      },
    }
  );

  return response.data.IpfsHash; // This is the CID
}

11.3 PostgreSQL + Prisma ORM

In modern blockchain projects, PostgreSQL is commonly used as the off-chain database, accessed through Prisma ORM (Object-Relational Mapping).

Prisma Schema Example:

// prisma/schema.prisma

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

generator client {
  provider = "prisma-client-js"
}

model Certificate {
  id            String   @id @default(cuid())
  certId        String   @unique    // blockchain certificate ID
  certHash      String              // keccak256 hash
  ipfsCid       String              // IPFS content identifier
  studentName   String
  studentEmail  String
  courseName    String
  issuerAddress String
  recipientAddr String
  status        String   @default("Active")
  issuedAt      DateTime @default(now())
}

model Institution {
  id      String @id @default(cuid())
  name    String
  address String @unique   // wallet address
}
Key insight: The database stores the SAME data as the blockchain for convenience (fast queries, search, UI display), but the blockchain version is the source of truth. If the database is deleted, the blockchain still has the permanent proof.

12.2 Ethers.js — The Bridge

Ethers.js is the most popular JavaScript library for interacting with Ethereum. It's the bridge between your web frontend and the blockchain.

Key Ethers.js Concepts:

Provider — Read Blockchain Data

import { ethers } from "ethers";

// Connect to a blockchain node (read-only)
const provider = new ethers.JsonRpcProvider("http://127.0.0.1:8545");

// Read blockchain data
const blockNumber = await provider.getBlockNumber();
const balance = await provider.getBalance("0x71C7...");

Signer — Write to Blockchain

// Connect to MetaMask (user can sign transactions)
const browserProvider = new ethers.BrowserProvider(window.ethereum);
await browserProvider.send("eth_requestAccounts", []);
const signer = await browserProvider.getSigner();

// signer can now send transactions
const tx = await signer.sendTransaction({
  to: "0xRecipientAddress...",
  value: ethers.parseEther("1.0")  // Send 1 ETH
});

Contract — Interact with Smart Contracts

// Read-only contract (no wallet needed)
const readContract = new ethers.Contract(
  contractAddress,
  contractABI,
  provider
);
const result = await readContract.verifyCertificate(certId);

// Write contract (needs MetaMask signer)
const writeContract = new ethers.Contract(
  contractAddress,
  contractABI,
  signer
);
const tx = await writeContract.issueCertificate(
  certHash, ipfsCid, recipient, name, course
);
await tx.wait(); // Wait for mining confirmation

13.3 Data Flow — Issuing a Certificate

Step 1 — Frontend (Browser)

User fills in student details and uploads a PDF certificate file. Clicks "Issue Certificate".

↓
Step 2 — Next.js API (Server)

The API route receives the form data and:

  • Reads the PDF as raw bytes
  • Computes certHash = keccak256(pdfBytes) — a unique fingerprint
  • Uploads the PDF to Pinata (IPFS) → gets back a CID
  • Saves a preliminary record in PostgreSQL
  • Returns the certHash and CID to the frontend
↓
Step 3 — MetaMask Transaction (Browser)

The frontend calls the smart contract's issueCertificate() function via Ethers.js:

  • MetaMask popup appears: "Confirm transaction? Gas: 0.003 ETH"
  • User clicks Confirm
  • MetaMask signs and sends the transaction to the blockchain
↓
Step 4 — Blockchain (Smart Contract)

The issueCertificate() function executes on-chain:

  • Checks: Is the caller an authorized issuer?
  • Creates a Certificate struct with all details
  • Stores it permanently in the contract's storage
  • Emits a CertificateIssued event
  • Returns a unique certId
↓
Step 5 — Confirmation (Frontend)

Frontend receives the confirmed transaction receipt, extracts the certId from the event, and updates the PostgreSQL record from "pending" to "Active".

13.4 Data Flow — Verifying a Certificate

1. Employer uploads the PDF to the verification page
↓
2. System computes keccak256(pdfBytes) = hash
↓
3. Calls contract.verifyCertificateByHash(hash) — a free view call
↓
4. Blockchain returns: VALID or INVALID + certificate details
Verification is FREE! Because it's a view function — it only reads data, doesn't modify the blockchain, so no gas is needed.

14. Tokens — ERC-20 & ERC-721 (NFTs)

14.1 What Are Tokens?

Tokens are digital assets created using smart contracts on Ethereum. They are NOT the same as ETH — they are built ON TOP of Ethereum.

14.2 ERC-20 — Fungible Tokens

Fungible = each token is identical and interchangeable (like dollar bills).

  • Examples: USDT, USDC, LINK, UNI
  • Used for: cryptocurrencies, stablecoins, governance tokens

ERC-20 Standard Functions:

interface IERC20 {
    function totalSupply() external view returns (uint256);
    function balanceOf(address account) external view returns (uint256);
    function transfer(address to, uint256 amount) external returns (bool);
    function approve(address spender, uint256 amount) external returns (bool);
    function transferFrom(address from, address to, uint256 amount) external returns (bool);
    function allowance(address owner, address spender) external view returns (uint256);
}

14.3 ERC-721 — Non-Fungible Tokens (NFTs)

Non-Fungible = each token is unique (like a painting).

  • Examples: CryptoPunks, Bored Ape Yacht Club, digital art
  • Each NFT has a unique tokenId
  • Used for: digital art, certificates, gaming items, real estate deeds
Certificates as NFTs: Some projects issue academic certificates as ERC-721 NFTs — each certificate is unique and permanently owned by the student's wallet address.

14.4 Comparison

FeatureERC-20 (Fungible)ERC-721 (NFT)
UniquenessAll tokens are identicalEach token is unique
DivisibleYes (e.g., 0.5 USDT)No (you can't own half an NFT)
Use CaseCurrency, utility tokensArt, certificates, collectibles
Example1 USDT = 1 USDTCryptoPunk #1234 ≠ CryptoPunk #5678

15. Gas & Transaction Fees

15.1 What Is Gas?

Gas is a unit that measures the computational effort required to execute operations on Ethereum. Every operation (storing data, computing, transferring) costs a specific amount of gas.

15.2 Gas Fee Calculation

Transaction Fee = Gas Used × Gas Price

Where:
  • Gas Used     = how much computation your transaction needed
  • Gas Price    = how much you pay per unit of gas (in Gwei)
  • 1 Gwei       = 0.000000001 ETH (1 billionth of an ETH)

Example:
  Gas Used  = 21,000 (simple ETH transfer)
  Gas Price = 30 Gwei
  Fee       = 21,000 × 30 Gwei = 630,000 Gwei = 0.00063 ETH ≈ $1.26

15.3 EIP-1559 Fee Structure (Current)

Since the London upgrade, Ethereum uses a two-part fee system:

ComponentDescription
Base FeeSet by the network, burned (destroyed). Adjusts based on network congestion.
Priority Fee (Tip)Extra payment to the validator — incentive to include your transaction faster.
Total Fee = Gas Used × (Base Fee + Priority Fee)

15.4 Gas Costs for Common Operations

OperationApproximate Gas
Simple ETH transfer21,000
ERC-20 token transfer~65,000
Deploy a contract~500,000 – 5,000,000
Store 32 bytes (one slot)20,000 (new) / 5,000 (update)
Call a view function0 (FREE!)
Important: On the Hardhat local network, gas still exists but it's free fake ETH — so you don't pay real money during development.

17. Security Best Practices

17.1 Common Smart Contract Vulnerabilities

VulnerabilityDescriptionPrevention
Reentrancy Attacker calls back into the contract before the first call finishes Use the Checks-Effects-Interactions pattern; use ReentrancyGuard
Integer Overflow Numbers wrap around (e.g., 255 + 1 = 0) Solidity 0.8+ has built-in overflow checks
Access Control Anyone can call admin functions Use onlyOwner modifiers; use OpenZeppelin's AccessControl
Front-Running Attackers see pending transactions and act first Use commit-reveal schemes
Denial of Service Contract blocked by failed external calls Use pull-over-push pattern for payments

17.2 Security Checklist

  • ✅ Use the latest Solidity version (0.8.x+)
  • ✅ Always validate inputs with require()
  • ✅ Use onlyOwner / access control modifiers
  • ✅ Never store private keys in code or Git
  • ✅ Use .env files for secrets
  • ✅ Test thoroughly before deploying
  • ✅ Use established libraries (OpenZeppelin)
  • ✅ Get your contract audited before mainnet deployment
